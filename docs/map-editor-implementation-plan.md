# ARUPIGI マップタイルエディタ実装計画書

作成日：2026-09-08

状態：計画作成済み・未実装

## 1. 目的と確定要件

Godotエディタ内で、現在のゲームに使われている2Dマップを見ながらタイルを手動配置できる、小規模な編集ツールを作る。

| 項目 | ユーザー確認済みの内容 |
| --- | --- |
| 用途 | タイルを手動配置するエディタ |
| 利用場所 | Godotエディタ内 |
| 対象 | 2Dマップ |
| 素材 | ゲームで使用中の素材から開始し、後から追加可能にする |
| 操作 | 配置、消去、元に戻すを中心とし、高機能化しない |
| 保存形式 | ゲームデータとして使える形式を実装側で選定 |

以下は既存実装に合わせた設計判断である。真上から見た正方形グリッド、地形1レイヤー、既存マップの編集を初期版の中心とする。保存形式には既存の `MapData` Resource（`.tres`）を採用する。

ユーザーの確定要件と実装側の補助仕様を次のように区別する。補助仕様は初期版を使いやすくするための提案であり、追加のユーザー要望として扱わない。

| 区分 | 内容 |
| --- | --- |
| 必須要件 | 手動配置、消去、元に戻す、既存素材の利用、素材追加、ゲーム用データの保存 |
| 実装側の補助仕様 | ドラッグ配置、Redo、スクロール・拡縮、目印表示、保存時の整合性確認 |
| 初期版の対象 | 既存3マップの地形編集。1度に開くマップは1つ |
| 後続拡張 | 新規マップ作成、サイズ変更、出入口などの編集。初期版では地形以外を保持する |

今回の成果物はこの計画書と文書間の案内である。第8・9節に記載する実装と動作検証は、実装着手後の作業とする。

本計画は追加開発の計画であり、[初期プロトタイプ実装計画](implementation-plan.md)の「独自マップ編集ツールは作らない」という当時の範囲を今回拡張する。

## 3. 画面と操作

Godot上部の作業画面切り替えに「マップ」を追加する。画面は次の構成とする。

| 領域 | 内容 |
| --- | --- |
| 上部 | マップ選択、保存、配置／消去、元に戻す／やり直す、消去後の下地選択、表示倍率 |
| 左側 | タイルパレット。サムネイル、地形ID、通行可否、素材一覧の更新ボタン |
| 中央 | 地形、グリッド、出入口・回復地点・出現位置の表示、配置予定セルの枠 |
| 下部 | マップ名、サイズ、セル座標、選択中の地形、未保存状態、検証メッセージ |

### 基本操作

1. マップ一覧から野原・町・洞窟などの `MapData` を開く。
2. パレットから地形を選ぶ。
3. 左クリックで1セル配置し、押したまま移動すると連続配置する。
4. 消去モードの左クリック、または右クリックで下地に戻す。
5. 「元に戻す」または `Ctrl+Z` で直前の操作を戻す。補助操作として「やり直す」と `Ctrl+Shift+Z` を用意する。
6. 保存ボタンまたは `Ctrl+S` で保存し、ゲームを起動し直して結果を確認する。

40×30セルの全体と細部を扱えるよう、スクロール移動と簡単な拡大縮小を用意する。ズームやスクロール後も同じセルを指せる座標変換に統一する。ショートカットは本ツールに操作フォーカスがある場合だけ処理し、テキスト入力中の操作を奪わない。

### 消去の定義

既存マップは全セルに有効な地形が必要なため、消去は「選択した下地タイルに置き換える」動作とする。透明セルや未定義の文字は作らない。

- 初期の下地は野原・町が平原、洞窟が床。
- 下地はパレット内の地形から変更でき、画面に常時表示する。
- その他のマップでは、利用可能な通行可能地形を初期候補にする。候補がない場合は下地の選択まで消去を無効にする。
- 下地の選択は編集補助設定であり、ゲームの `MapData` にフィールドを追加しない。
- 出入口・回復地点などの目印は地形と別データなので、消去しても削除しない。

### ドラッグと履歴

- マウスを押してから離すまでを1回の操作とする。
- 高速にドラッグした場合も、前回セルと現在セルの間を補間して塗り残しを防ぐ。
- 同じセルを何度通過しても、変更前の値は最初の1回だけ保持する。
- 同じ地形への上書きやマップ外の操作では履歴を増やさない。
- 範囲外では描かず、キャンバスから外れてもボタン解放を検知する。フォーカス喪失時は途中までの変更を1操作として確定する。
- Undoで配置だけでなく、その操作が追加した地形の文字対応も戻す。Redoで両方復元する。
- マップ切り替え時に前のマップの履歴を終了し、別マップへ誤適用しない。

## 4. タイル素材の追加方法

パレットは `data/terrains/` 以下の `TerrainData` Resourceを走査して作る。画像フォルダーを直接一覧化すると敵や人物も混ざるため、地形Resourceを登録単位にする。

利用者は次の手順で追加できる。

1. `assets/art/` などプロジェクト内に新しい画像を追加する。
2. Godot標準のResource作成操作で `TerrainData` を作り、`data/terrains/` 以下に `.tres` として保存する。
3. 一意の地形ID、テクスチャ、通行可否をインスペクターで設定する。
4. ツールの「素材一覧を更新」で読み込み、パレットから配置する。

初期版の素材登録UIはGodot標準インスペクターを利用する。画像の切り出しやタイルアトラスの作成機能は設けない。48×48を推奨し、その他の画像もセルの描画サイズに合わせて表示する。

`rows` が1セル1文字の形式であるため、新しい地形を初めて配置する時に、対象マップの `terrains` に未使用の1文字キーを自動割り当てする。既存キーは維持し、同じResourceには既存キーを再利用する。追加キーは英数字から決定的な順序で選び、空きがなければ配置前に理由を表示する。複数文字キーへの拡張や既存マップ全体の再符号化は行わない。

すでにマップが参照している地形は、標準の素材フォルダー外でもパレットに表示する。ID重複やテクスチャ欠落のある追加素材はエラーを表示し、新規配置対象にしない。

## 5. 保存とゲームへの反映

### 編集対象と保持するデータ

初期版で変更するのは `rows` と、新規地形の利用に必要な `terrains` の対応だけとする。以下は表示または保持し、専用の編集UIを追加しない。

- マップID、表示名、幅・高さ。
- 出現位置 `spawns`。
- 出入口 `portals` と移動先。
- 回復地点 `healing_cells`。
- 遭遇の有効設定と敵候補。

既存マップの寸法変更、新規マップ作成、出入口の配置は後続拡張とする。形式が正しい別の `MapData` を開くことは可能にするが、新しいファイルをゲームの `MAPS` に登録する処理は自動化しない。

### 保存手順

1. 読み込み時に編集用の作業データを用意し、共有Resourceの `rows` や辞書を直接変更しない。地形・敵の外部Resource参照は維持する。
2. 保存前に第6節の検証を行う。
3. 読み込み時または直近の保存成功時のファイル内容と比較し、保存先が外部変更されていないか確認する。変更があれば作業内容を保持して上書きを止め、再読み込みを案内する。再読み込みで作業内容を破棄する前に確認する。
4. 保存用の `MapData` に編集内容を適用し、元の `.tres` に保存する。保存結果を確認するまで未保存表示を解除しない。
5. 保存に失敗した場合は作業内容と履歴を保持し、理由を表示する。既存ファイルを壊さないため、一時ファイルへの保存・再読み込み確認から置き換える方式を実装時に検証する。
6. 保存後は外部変更検知の比較元を更新し、Godotのファイルシステムとキャッシュに変更を反映する。閉じて開き直しても保存内容が一致することを確認する。

GodotのResource保存には `ResourceSaver` を用いる。[Godot 4.6 ResourceSaver](https://docs.godotengine.org/en/4.6/classes/class_resourcesaver.html)

マップ切り替え時の未保存変更は「保存／破棄／キャンセル」で扱う。終了時の未保存通知と保存連携には `EditorPlugin` の仕組みを利用する。プラグイン無効化時にも変更を黙って失わないよう、通常の通知が利用できない経路では作業用復旧データを残し、次回有効化時に案内する。[Godot 4.6 EditorPlugin](https://docs.godotengine.org/en/4.6/classes/class_editorplugin.html)

未保存状態は最後に正常保存した編集内容との比較で判定する。Undoで保存済み状態に戻れば表示を解除し、Redoで異なる状態になれば再表示する。保存自体は履歴を消さない。

保存した既存3マップは、次回のゲーム起動時に現在の `MAPS` の読み込み経路で使われる。実行中ゲームへの即時反映は初期版の対象外とする。

## 6. 保存可能な形式とゲーム内の動線の検証

データ形式の不正と、編集中の通路・出入口の問題を区別する。読み込みに必要な形式が不正な場合は保存を止める。通路を作り直している途中でも作業を保存できるよう、到達可能性などの問題は座標付きで表示し、保存自体は許可する。ゲームへの採用時には両方を解消し、第9節の検証を通す。

| 検証 | 判定内容 | 保存時の扱い |
| --- | --- | --- |
| 配列の整合 | 幅・高さが正、行数が高さと一致、各行の文字数が幅と一致 | 不正なら保存不可 |
| 地形定義 | 使用文字に `TerrainData` とテクスチャがあり、対応キーが1文字 | 不正なら保存不可 |
| 重要セル | 出現位置・出入口・回復地点が範囲内かつ通行可能 | 問題を表示して保存可 |
| 出現位置 | 1つ以上定義され、出入口セルと重ならない | 問題を表示して保存可 |
| 到達可能性 | 基準の出現位置から4近傍の通行可能セルをたどり、全出現位置・出入口・回復地点へ到達できる | 問題を表示して保存可 |
| 移動先 | ゲームに登録された対象マップと出現位置が存在する | 問題を表示して保存可 |
| 遭遇設定 | 遭遇が有効な場合は有効な敵候補がある | 問題を表示して保存可 |

到達可能性の基準は、野原では `start`、町・洞窟では `entry`、その他ではID順の最初の出現位置とする。基準セルが不正ならその問題を先に表示し、探索処理は行わない。問題のある途中状態を保存しても「ゲームで検証済み」とは扱わず、修正後の再検証を必要とする。

読み込み時に構造不正がある場合は、描画例外を起こさず原因を表示する。復元不能な構造は編集を無効にし、勝手な補正保存をしない。

既存 `tests/integration_test.gd` の整合性確認と同じ基準を使い、共通化する場合はデータだけで動作する検証ヘルパーへ抽出する。ゲーム固有の移動先一覧は検証側から渡し、ツールがゲーム本体を起動する依存関係は作らない。

## 7. 実装構成

| ファイル案 | 責務 |
| --- | --- |
| `addons/map_editor/plugin.cfg` | プラグイン情報 |
| `addons/map_editor/plugin.gd` | `EditorPlugin`、画面登録、保存・終了連携 |
| `addons/map_editor/map_editor_panel.gd` | マップ選択、パレット、操作ボタン、状態表示 |
| `addons/map_editor/map_canvas.gd` | 地形と目印の描画、座標変換、ドラッグ、表示倍率 |
| `addons/map_editor/map_edit_document.gd` | 作業データ、操作履歴、文字割り当て、未保存判定、保存 |
| `scripts/data/map_validator.gd` | マップデータの整合性・到達可能性の検証 |
| `tests/map_editor_test.gd` | 配置・消去・履歴・保存互換性の検証 |
| `docs/map-editor-guide.md` | 有効化、操作、素材追加、ゲームへの反映手順 |

エディタ上で動くスクリプトに `@tool` を付ける。UIの構築方式は既存プロジェクトと同様にGDScript中心とし、不要なシーン構造を増やさない。

履歴には作業データ専用の `UndoRedo` を使用し、専用キャンバスの操作をまとめる。ゲームのシーン編集やインスペクター操作の履歴とは独立させる。[Godot 4.6 UndoRedo](https://docs.godotengine.org/en/4.6/classes/class_undoredo.html)

`MapController` を編集画面に直接起動すると衝突ノードなども生成されるため、キャンバスではテクスチャと目印だけを描画する。表示規則とタイルサイズはゲーム側に合わせる。

## 8. 実装順序と各段階の完了条件

| 段階 | 作業 | 完了条件 |
| --- | --- | --- |
| 1. 読み込みと画面 | プラグイン登録、マップ選択、既存素材パレット、キャンバス、移動・拡縮 | 3マップを既存の地形・目印付きで表示できる |
| 2. 配置と消去 | セル入力、ドラッグ補間、下地選択、作業データ分離 | 表示倍率を変えても指定セルを編集でき、未保存の元ファイルを変更しない |
| 3. 履歴 | ストローク単位のUndo／Redo、未保存状態、マップ切り替え | 1回のドラッグを1回で戻せ、別マップへ履歴が混ざらない |
| 4. 保存と検証 | Resource保存、重要セル・到達可能性の検証、外部変更検知、終了時処理 | 再読み込み結果が一致し、地形以外の設定と外部参照が保たれる |
| 5. 素材追加 | Resource一覧更新、新しい地形の文字割り当て | 新素材をコード変更なしで配置・保存し、ゲームで表示できる |
| 6. 通し確認と文書 | 自動検証、Godot上の操作、ゲームの移動確認、操作ガイド | 第9節を満たし、有効化から素材追加まで文書どおりに実行できる |

段階1〜4を優先し、既存マップを編集してゲームに反映する経路を完成させてから素材追加を仕上げる。

## 9. 検証計画と完成条件

### 自動検証

- 配置・消去・連続描画・境界外入力で、対象セルだけが変更される。
- 1ストロークの複数セルと地形対応がUndo／Redoで完全に復元される。
- 無変更の操作で履歴が増えず、保存後のUndo／Redoで未保存状態が正しく変わる。
- `.tres` 保存後の再読み込みで、配置・寸法・全メタデータ・外部Resource参照が一致する。
- 編集用データを変更しても、保存前の共有Resourceを変更しない。
- 新規地形のキー割り当て、既存キー再利用、キー不足を正しく処理する。
- 出入口を壁で塞ぐ、重要地点を孤立させる、素材が欠落するなどの不正を検出する。
- 通路が未完成でも形式が正しければ保存でき、形式不正の場合は保存を止める。
- 保存失敗・外部変更時に、元ファイルと編集内容を失わない。
- 保存成功後の再編集・再保存を、自分の前回保存との競合として誤検知しない。

保存関連のテストは `build/` 以下の一時マップを使用し、実際のゲーム用マップをテストのために上書きしない。

既存の `logic_test.gd` と `integration_test.gd` を実行し、ゲーム側の既存機能が保たれることも確認する。テストで固定座標の地形に依存する部分があるため、ツール動作確認用の配置を製品マップに残さない。

### Godot上の手動検証

1. プラグインを有効化し、3マップを切り替える。
2. 配置、消去、高速ドラッグ、拡縮後の入力、キャンバス外へのドラッグを確認する。
3. Undo／Redo、保存済み状態への復帰、未保存での切り替え・終了・無効化を確認する。
4. 目印を確認しながら編集し、不正な通路変更の理由が画面に出ることを確認する。
5. 素材を1種類追加して配置・保存し、Godotを開き直しても読み込めることを確認する。
6. 保存したマップでゲームを新規起動し、見た目、通行可否、町・洞窟への出入り、回復を確認する。

GodotはREADME記載の4.6.2実行ファイルを使う。現段階ではWindowsビルドの作成・テストを完了条件に含めず、エディタからの実行で検証する。

完成条件は「既存素材と追加素材を使って既存マップを配置・消去・Undoでき、保存後にゲームが同じ配置と通行判定で動作すること」とする。

## 10. 初期版に含めない機能

- 自動生成、オートタイル、隣接地形への自動接続。
- 塗りつぶし、矩形選択、コピー＆ペースト、複数セルブラシ。
- 複数レイヤー、アニメーションタイル、アイソメトリック、六角形、3D。
- 新規マップ作成・リサイズ・ゲームへの自動登録。
- 出入口、出現位置、回復地点、敵配置の専用編集UI。
- 素材画像の制作・切り出し、アトラス編集。
- 実行中ゲームとの同期、外部マップ形式との相互変換。

上記は必要になった時点で追加する。素材追加は初期版の必須要件として実装する。
